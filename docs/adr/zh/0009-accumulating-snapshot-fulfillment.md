# ADR-0009：订单履约的累积快照事实表

[日本語](../ja/0009-accumulating-snapshot-fulfillment.md) | [English](../en/0009-accumulating-snapshot-fulfillment.md) | **中文**

**状态：** 已采纳

## 背景
`fact_order_item` 是事务事实表（每个订单明细一行），能回答"卖了什么"，却回答不了"从下单到送达，时间花在了哪里"。这是订单整个生命周期的属性：下单 → 审核 → 交给承运商 → 送达，或者取消／缺货。

## 决策
- **`gold.fact_order_fulfillment`**：累积快照，**每个订单一行**，每到一个新阶段就原地更新这一行（按 `order_id` MERGE，内容哈希变了才重写）。
- **数据来源是新增的 `silver.order_changes`**：一张只追加的日志，保存每一条校验通过的状态变更，键为 `(order_id, change_seq)`，从不更新。`silver.orders` 只保存当前状态，日志保存的是走到这个状态的过程。取消／缺货订单的结束时间从这里取得，它同时也是审计记录。它是**一条带独立 checkpoint 的单独数据流**，所以已有环境在下一次运行时会自动从 Bronze 回填全部历史。规则只为过滤而重新评估，隔离和指标仍只由 `orders` 记录一次。
- **各阶段时间**取自该订单最新的一条变更（变更后镜像带着到当时为止的全部时间戳）。结束取第一条 `canceled`／`unavailable` 变更，原因写入 `end_reason`。
- **时长以小时为单位**：`hours_to_approve`、`hours_to_ship`、`hours_in_transit`、`hours_total`，以及 `hours_late`。`hours_late` 从预计送达日的**结束时刻**算起，因为预计送达是一个日期，这样和 `is_on_time` 保持一致。
- **角色扮演日期键**：每个阶段一个日期键，都指向 `dim_date`。按照 Kimball 的做法，日期键**从不为 NULL**：还没发生的阶段指向 `dim_date` 里一行特殊记录 `-1`（"尚未发生"）。这样关联时不会丢掉未完成的订单，BI 工具里显示的也是标签而不是空白。
- **不放卖家列。** 一个订单可能包含多个卖家，按卖家的分析仍用 `fact_order_item`。订单层面的度量是 `item_count` 和 `order_value`。

## 时间戳不一致
某个阶段的时长算出来是负数时，设为 NULL，并给订单打上 `has_inconsistent_milestones` 标记；原始时间戳保持原样。每次运行都会向 `ops.dq_metrics` 写入一条警告级别的指标 `inconsistent_milestones`（闸门不看它）。

真实数据中，82,406 个订单里有 628 个（0.76%）被标记：

| 不一致的类型 | 订单数 |
|---|---:|
| 审核之前就交给了承运商 | 559 |
| 下单之前就交给了承运商 | 46 |
| 交给承运商之前就送达 | 23 |

大多数只差几分钟，像是系统之间的时钟误差；相差几个月的只有少数。

**已知漏洞：** Silver 的规则 `change_before_purchase` 只隔离触发它的那一条变更。后续变更都是变更后镜像，仍带着错误的交接时间，于是这个时间进入了 `silver.orders`（46 个订单）。本 ADR 不改 Silver 的行为，而是在 Gold 用标记处理。要在 Silver 修复，就得把具体的时间戳置为 NULL，那是另一个决策。

## 把满意度放在延误旁边
这是在一位读者问到"延误如何影响客户满意度"之后加上的。事实表增加了 `review_score`（订单评分的平均值，一个订单可能有多条评价）和 `review_count`。没有评价的订单评分保持为 NULL，不做任何填补。真实数据中已送达且有评价的订单：

| 送达情况 | 订单数 | 平均评分 | 1–2 星占比 |
|---|---:|---:|---:|
| 准时 | 71,451 | 4.27 | 9.4% |
| 迟到 | 5,505 | 2.21 | 64.1% |

按迟到程度：提前 7 天以上 4.30，提前 0–7 天 4.08，迟到 1–3 天 3.22，迟到 4–7 天 2.07，迟到 8 天以上 1.66。Olist 没有其他客户触点的数据（客服联系、浏览等），所以这里只覆盖配送体验。评价在送达之后才会到来，所以最近的订单还没有评分（和各阶段时长一样，存在右删失）。

## 考虑过的备选方案
- **只从 `silver.orders` 取各阶段时间：** 简单，但没有取消订单的结束时间，也没有历史。
- **直接读 Bronze：** 未校验的数据会进入 Gold。
- **把小的负值当作时钟误差（N 小时以内按 0 处理）：** N 只能是拍脑袋的数字。留作业务方定义了容忍范围时的选项。
- **排除被标记的订单：** 会悄悄丢掉 0.76% 的订单。

## 影响
- 右删失（right-censoring）：最近的月份里只有完成得快的订单才有完整的阶段，平均值会偏低。Dashboard 上已注明。
- 用 Change Data Feed 让 Gold 增量化是下一步，会同时应用到两张事实表。
- 测试：`tests/test_fulfillment.py`（各阶段时间、小时数、日期键、准时的边界、未完成订单、结束原因、不一致的时间戳、原地更新、只追加日志），以及两项端到端检查。
