# ADR-0010：每日订单积压的周期快照

[日本語](../ja/0010-periodic-snapshot-backlog.md) | [English](../en/0010-periodic-snapshot-backlog.md) | **中文**

**状态：** 已采纳

## 背景
项目里已经有 Kimball 三种事实表中的两种：事务事实表（`fact_order_item`）和累积快照（`fact_order_fulfillment`，ADR-0009）。它们都回答不了"某一天，各个阶段卡着多少订单？情况是不是在变坏？"这是一个关于**按固定间隔记录的状态**的问题，正是周期快照的用途。Olist 没有库存或余额类的数据，但重放只追加的变更日志（`silver.order_changes`），就能知道过去任意一天每个订单所处的状态。

## 决策
- **`gold.fact_daily_order_backlog`**：每一行是**某一天 × 某个未完成状态 × 某个客户所在州**，从第一个订单（2016-09-04）到日志里的最后一天。未完成状态是 created、approved、invoiced、processing、shipped；已送达、已取消、缺货的订单离开积压。
- 订单在 D 日的状态，取 D 日及之前的变更里 `change_seq` 最大的那一条的状态。从下单日开始计数，所以即使有日期早于下单的变更，订单也不会提前出现。
- **度量**：未完成订单数、金额、已过去天数的中位数、超过 30 天未完成的订单数、已过预计送达日期的订单数。这些度量是半可加的：可以跨州、跨状态相加，但不能跨日期相加。
- **用客户所在州，而不是卖家**：一个订单只有一个客户，但可能有多个卖家。缺失的州记为 `unknown`，绝不为 NULL，因为 NULL 的合并键永远匹配不上，每次运行都会产生重复行。
- **卡住的订单保留**：真实数据里有 677 个订单停在 processing／invoiced／created，永远不会结束。它们被保留下来并可以被衡量（超过 30 天、已逾期），用中位数避免它们扭曲年龄。

## 按事件时间，而不是到达时间
日期是变更**发生**的那一天。Kimball 经典的周期快照每个周期只写一次，之后不再修改（"周期结束时已知的情况"）。这里有意不这样做：
- 98% 的历史（323,868 条变更中的 316,276 条）都在唯一一次回填批次里到达，按"到达当天已知的情况"计算，会把两年的历史堆到一天上。
- 迟到的变更属于它发生的那一天，所以已经发布的日子必须被修正。

快照每次运行都从日志重建，并按粒度做 MERGE：变化的行更新，新的组合插入，**不再存在的组合删除**（`whenNotMatchedBySourceDelete`）。每一次修正都能在 Delta 历史里看到。

## 真实数据上的结果
- 共 53,836 行；最后一天有 3,827 个未完成订单，与 `fact_order_fulfillment` 中的未完成订单数完全一致。
- 积压的峰值是 2018-03-25 的 5,428 个未完成订单。
- 逾期订单从 2017 年初的每天约 30 个，增长到 2018 年 4 月的每天约 1,700 个。很多订单被标记为已发货，却一直没有送达日期，于是不断累积。最后一天有 1,150 个已发货订单处于逾期状态。

## 考虑过的备选方案
- **按到达时间、只追加：** 经典定义，但在这份数据上历史部分没有意义。
- **每个未完成订单每天一行：** 为了同样的答案要几千万行。
- **每次运行都覆盖整张表：** 更简单，但修正过程就看不到了。
- **把超过 N 天的订单去掉：** N 只能是拍脑袋的数字，还会掩盖真实的问题。

## 影响
- 每次运行都重新计算全部历史（在这个规模下只要几秒）。只重建受新变更影响的日期，属于下一步 Change Data Feed 的范围。
- 测试：`tests/test_backlog.py`（当天结束时的状态、离开积压、度量、卡住的订单、下单之前的变更、不为 NULL 的键、带删除的修正），以及两项端到端检查：重跑结果不变、最后一天与履约事实表的未完成订单数一致。
