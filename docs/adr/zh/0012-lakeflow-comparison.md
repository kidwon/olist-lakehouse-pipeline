# ADR-0012：用 Lakeflow 声明式管道实现同一套规格，并排对比

[日本語](../ja/0012-lakeflow-comparison.md) | [English](../en/0012-lakeflow-comparison.md) | **中文**

**状态：** 已采纳

## 背景
ADR-0008 为了展示机制本身选择了命令式（Structured Streaming + MERGE），并说这些机制在 Lakeflow 里"各只需一个关键字"。这份 ADR 就来验证这个说法。我们在 `lakeflow/` 里用声明式重写了四个机制（读取文件、只前进的 CDC、由快照生成卖家 SCD2、带隔离的订单明细质量检查），外加 Gold 的事务事实表。SQL 写不了的部分用 Python。管道读取**同一批投递文件**，写到单独的库 `olist_sdp`，这样两边可以核对。免费版每种管道同时只能有一个在运行，所以做成触发运行，而不是持续运行。

| Silver 订单明细（行数；键） | 93,465 | 93,465 | 一致 |

| 关联不到卖家版本的事实行 | 0 | 91,085（97%） | **设计上的差异** |

## Lakeflow 更简单的地方
- **代码量：** 同样的机制，命令式约 450 行，Lakeflow 约 145 行（SQL + Python）。不是严格的一一对比，但差距是真实的。
- **只前进的 CDC** 只要一个 `AUTO CDC ... SEQUENCE BY change_seq` 流，checkpoint 和 MERGE 条件都不需要了。
- **去重**用以业务键为键的 `AUTO CDC` 就能完成。
- **质量指标自动得到：** 事件日志按每条规则记录通过和失败的行数，数量和 `ops.dq_metrics` 完全一致。
- **快照有版本：** `AUTO CDC FROM SNAPSHOT` 只应用比上一份更新的快照。核对表明，这一点防住了命令式版本漏掉的问题（见下一节）。

## 对比中发现的命令式版本的问题
设置作业被手动重新运行，回放被重置，2018-05-31 的回填文件被重新投递。命令式的 SCD2 把旧快照当成了变化，把 78 个迁址的卖家改回了原来的城市，产生了"结束早于开始"的版本。Lakeflow 忽略了这份重新投递的快照。命令式版本的修复：
- `scd2.apply_snapshot` 会跳过不比上一份新的快照（上一份的日期保存为表属性），并加了回归测试，没有修复时测试会失败。
- `replay.prepare` 在已经投递过批次的情况下，除非指定 `--force`，否则拒绝重置回放。
- 在 Databricks 上用 `RESTORE TABLE ... TO VERSION AS OF 12`（Delta 的时间旅行）把表恢复，再用 `full_refresh=true` 重建 Gold。

## Lakeflow 需要变通、或做不到规格要求的地方
- **SCD2 的第一个版本：** 规格（ADR-0003）规定卖家的第一个版本从 1900-01-01 开始。Lakeflow 从第一份快照的日期开始，所以**97% 的事实行（2018-05-31 之前的订单）关联不到任何卖家版本。** 这样的业务规则需要在上面再加一层，简洁性也就丢掉了大半。
- **历史快照需要 Python：** SQL 写法只对表当前的样子拍快照。要按顺序回放每天一份的快照，需要带版本函数的 `create_auto_cdc_from_snapshot_flow`。
- **隔离需要第二张表：** 质量规则只会丢弃并统计坏行，不会保存。要用反过来的同一组规则把坏行写进隔离表，所以每条规则都要写两遍。
- **闸门只能模拟：** 对汇总结果使用 `EXPECT ... ON VIOLATION FAIL UPDATE`，会让整次更新失败，而不只是 Gold。而且每次更新都会重新评估收到过的所有批次，只要历史上有一个坏批次，在处理掉它之前，以后的每次更新都会失败。
- **无法在本地测试：** 管道只能在 Databricks 上运行；命令式代码可以在笔记本电脑和 CI 上用 pytest 运行（64 个测试加 notebook）。这里的正确性只能靠核对来保证。

## 决策
本仓库继续以命令式管道为主要实现：它可以端到端测试，也能准确表达业务规则（从 1900 年开始的版本、只阻止 Gold 的比例闸门）。Lakeflow 版本保留为参考实现和核对手段。对于没有这类业务规则的新团队管道，以 Lakeflow 为默认是合理的：代码少得多，指标和快照版本管理也是现成的。

- `resources/olist_sdp.yml` 随部署配置一起部署这条管道；讲解 notebook [`10_lakeflow_comparison`](../../../notebooks/walkthrough/10_lakeflow_comparison.py) 在 Databricks 上运行核对。
