# ADR-0013：两套完整实现，每天对账

[日本語](../ja/0013-two-implementations.md) | [English](../en/0013-two-implementations.md) | **中文**

**状态：** 已采纳。取代 ADR-0012 的决定（声明式只作参考）。

## 背景
ADR-0012 用 Lakeflow Spark Declarative Pipelines 重写了四个机制和一张事实表，并把命令式管道保留为唯一的正式实现。理由是三个缺口：一条业务规则（卖家第一个版本从 1900 年开始）、只挡 Gold 的闸门，以及不能在本地测试。写完声明式版本后发现，需要维护的东西少得多，于是目标变了：把整套规格也用声明式做成正式实现。

## 决定
- **两套实现都完整，地位平等。** `lakeflow/` 现在会生成命令式代码生成的所有表：Bronze、规则检查、隔离表、全部 Silver 表、指标、闸门、全部维度表、三种事实表和汇总表。写入 `olist_sdp` 库。
- **每天并行运行。** `olist_daily` 投递当天批次后，让命令式任务和声明式管道并行运行，然后由 `olist reconcile` 逐行比较 16 张表（双向 `EXCEPT ALL`），只要有差异就让作业失败。
- **命令式版本是"标准答案"。** 声明式管道不能在本地运行；命令式版本在本地有单元测试和端到端测试。每天的对账就是声明式版本的测试。
- **每套实现一个看板**，由同一个脚本生成。

## 缺口怎么补上的
| 缺口（ADR-0012） | 声明式的解决办法 |
|---|---|
| 规则写两遍（expectation 和隔离表各一遍） | 每张 `checked_*` 表把一行违反的规则列在 `_failed_rules` 里，规则只写一次。expectation 只按名字引用这些规则（不指定动作），所以事件日志仍然按规则计数；之后隔离表和 Silver 再把行分开。 |
| 卖家第一个版本从第一份快照开始（97% 的事实行没有卖家） | `dim_seller` 把 `AUTO CDC FROM SNAPSHOT` 的历史整理一遍：最早的版本从 1900-01-01 开始，`seller_sk = xxhash64(seller_id, valid_from)`，和命令式的键相同。 |
| 闸门会停掉整次更新，而不只是 Gold | 作业用 `refresh_selection` 把管道分两次刷新：第一次刷新 Bronze、Silver、隔离表、指标和 `dq_gate`，第二次刷新 Gold。`dq_gate` 超过 5% 就让自己这次刷新失败，Gold 的刷新就不会开始。已在 Free Edition 上验证：不在选择范围内的表显示为 `EXCLUDED`；失败的刷新里写入的 Silver 会保留，下次刷新也不会重复写入。管道默认会重试失败的更新，但数据问题重试只会推迟失败，所以把 `pipelines.numUpdateRetryAttempts` 设为 0。测试时把阈值降到 0.1%，作业在 3 分钟内失败，`sdp_gold` 被跳过（`UPSTREAM_FAILED`）。 |
| 闸门每次都重新检查历史上所有批次 | `dq_gate` 只看最新批次。 |
| 不能在本地测试 | 每天和测试过的命令式版本对账。 |
| 增量 Gold 要自己写（ADR-0011） | Gold 表都是物化视图；平台决定每张怎么刷新，并记录在事件日志里（发布为 `olist_sdp.event_log`）。全量刷新时整张重算；上游没有新数据的更新是 `NO_OP`。 |

## 对账发现了什么
1. **按读取时间给重新投递的数据排序。** 第一次全量刷新时，有 10 行订单明细（以及由它们生成的事实表）对不上。全量刷新会一次读取所有日期的文件，所有行的读取时间都一样，"保留第一次投递"就成了随机选一份；如果留下的是第二天重新投递的那份，到达延迟就会多算一天。现在两套实现都按文件路径里的投递日期排序（`silver.py` 的 `first_delivery` / `latest_delivery`，声明式数据流的 `SEQUENCE BY`）。命令式的订单明细之前只是碰巧正确：它的平局判断用的是文件路径，而路径恰好以日期开头。客户和评论则完全没有按日期排序。
2. 修复之后，**16 项检查全部一致**：6 张 Silver 表、4 张维度表、3 张事实表、汇总表、隔离表和规则指标。

## 仍然存在的差异（设计如此）
- **闸门的含义。** 命令式闸门判断的是本次运行的输入，没有新数据的运行会通过。声明式闸门判断的是最新批次，所以只要有一个坏批次，在数据修好之前 Gold 会一直停住。两者都保护 Gold，声明式更严格。
- **没有闸门日志。** 声明式的看板按批次（从指标表）显示闸门结果，而不是按运行显示。
- **隔离表和指标按集合比较**，去重相关的计数（info）不比较：命令式的运维表在重新处理某个批次时会再追加一遍。
- **`refresh_selection` 是作业管道任务的测试版功能。**

## 代码量
不算注释和空行，声明式是约 550 行 SQL 和 Python，命令式在同样范围（Bronze、质量、Silver、SCD2、闸门、Gold、增量）是约 1,070 行 Python。声明式的 SQL 比 ADR-0012 的 145 行长，是因为现在包含了整套规格，还包括和命令式 Bronze 完全相同的 JSON 解析。

## 影响
- `olist_daily` 多了三个任务：`sdp_silver_and_gate`、`sdp_gold`、`reconcile`。结果追加到 `olist_ops.reconcile_log`。
- `tests/test_pipeline_e2e.py` 会检查每个参与对账的列在命令式的表里都存在，所以改了列名会在本地失败，而不是等到每日作业才失败。
- 讲解 notebook 10 会运行对账，并展示缺口是怎么补上的。
