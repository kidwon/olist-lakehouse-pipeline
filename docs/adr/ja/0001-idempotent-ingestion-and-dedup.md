# ADR-0001: 冪等な取り込みと重複排除

**日本語** | [English](../en/0001-idempotent-ingestion-and-dedup.md) | [中文](../zh/0001-idempotent-ingestion-and-dedup.md)

**ステータス:** 採用

## 背景
注文明細フィードは追記専用ですが、送信元は同じ明細を再送してきます。同じバッチ内で二重に届くことも、翌日に再び届くこともあります。また、ジョブはリトライされることがあります。これらがファクトテーブルに到達すると、売上が二重計上されます。

## 決定
重複は二つの段階で除去し、段階ごとに異なるケースを捕捉します。

1. **ファイル単位:** Bronze は Auto Loader（ローカルではファイルストリームソース）を `trigger(availableNow=True)` とチェックポイント付きで読み込みます。各ファイルは一度だけ取り込まれるため、リトライしても新しいデータはありません。
2. **行単位（バッチ内）:** `keep_first` が業務キー `(order_id, order_item_id)` ごとに `row_number()` で1行に絞ります。
3. **行単位（バッチ間）:** Silver の MERGE は `WHEN NOT MATCHED THEN INSERT` のみです。既に保持しているキーは「再送」とみなし、更新としては扱いません。

行単位の除去件数は `duplicate_in_batch` と `duplicate_already_loaded`（重要度 `info`）として `ops.dq_metrics` に記録します。重複を黙って吸収するのではなく、可視化します。

## 検討した代替案
- **ストリーム上で `dropDuplicates` とウォーターマークを使う:** 重複が届き得る期間に上限を設ける必要があり、ステートも保持し続けます。テーブルに対する MERGE なら期間の制約がありません。
- **毎回 Bronze から Silver を全件上書きする:** 単純ですが、コストが履歴量に比例して増え、リトライのたびに全件を再処理します。

## 影響
- 明細を訂正するには、新しいキーか明示的な更新フィードが必要です。これはソースの契約（「行は追加のみ」）と一致します。
- テスト: `test_redelivered_item_is_not_counted_twice`、および「Silver の件数 = 配信件数 − 重複 − 隔離」を検証する E2E テスト。
