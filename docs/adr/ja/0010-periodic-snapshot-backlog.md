# ADR-0010: 日次注文残の定期スナップショット

**日本語** | [English](../en/0010-periodic-snapshot-backlog.md) | [中文](../zh/0010-periodic-snapshot-backlog.md)

**ステータス:** 採用

## 背景
このプロジェクトには、Kimball の3種類のファクトのうち2つがありました。トランザクション・ファクト（`fact_order_item`）と累積スナップショット（`fact_order_fulfillment`、ADR-0009）です。どちらも「ある日、各段階に何件の注文が止まっていたか、そしてそれは悪化しているか」には答えられません。これは**一定間隔での状態**についての問いであり、定期スナップショットの役割です。Olist には在庫や残高のフィードはありませんが、追記専用の変更ログ（`silver.order_changes`）を再生すれば、過去の任意の日の各注文のステータスが分かります。

## 決定
- **`gold.fact_daily_order_backlog`**：**日付 × 未完了ステータス × 顧客の州**ごとに1行で、最初の注文（2016-09-04）からログの最終日までを対象とします。未完了のステータスは created、approved、invoiced、processing、shipped です。配達済み・キャンセル・在庫切れの注文は注文残から外れます。
- ある注文の D 日のステータスは、D 日以前の変更のうち `change_seq` が最大のもののステータスです。購入日から数えるため、購入日より前の日付を持つ変更があっても、注文が早く現れることはありません。
- **指標**：未完了の注文数、その金額、経過日数の中央値、30日を超えて未完了の注文数、配達予定日を過ぎた注文数。指標は半加算的で、州やステータスをまたいで足せますが、日付をまたいで足すことはできません。
- **セラーではなく顧客の州**：1つの注文の顧客は1人ですが、セラーは複数になり得ます。州が欠けている場合は NULL ではなく `unknown` にします。NULL のマージキーは一致しないため、実行のたびに重複が生じるからです。
- **止まった注文は残す**：実データでは 677 件の注文が processing / invoiced / created で止まったまま完了しません。これらは残したうえで測れるようにし（30日超、期限切れ）、中央値を使うことで経過日数が歪まないようにしています。

## 到着時刻ではなくイベント時刻で数える
日付は、変更が**起きた**日です。Kimball の古典的な定期スナップショットは、各期間を一度だけ書き、以後変更しません（「期間の終わりの時点で分かっていたこと」）。ここでは意図的にそうしていません。
- 履歴の98%（323,868 件中 316,276 件の変更）が1回のバックフィルで届いているため、「届いた日の時点で分かっていたこと」で数えると、2年分の履歴が1日に積み上がります。
- 遅れて届いた変更は起きた日に属するため、既に公開した日を修正する必要があります。

スナップショットは毎回ログから作り直し、粒度キーで MERGE します。変わった行は更新し、新しい組み合わせは挿入し、**存在しなくなった組み合わせは削除します**（`whenNotMatchedBySourceDelete`）。すべての修正は Delta の履歴で確認できます。

## 実データでの結果
- 53,836 行。最終日の未完了注文は 3,827 件で、`fact_order_fulfillment` の未完了注文とちょうど一致します。
- 注文残のピークは 2018-03-25 の 5,428 件です。
- 期限切れの注文は、2017年初めの1日あたり約30件から、2018年4月には約1,700件に増えています。発送済みのまま配達日が記録されない注文が多く、それが積み上がっていきます。最終日には、発送済みの注文 1,150 件が期限切れです。

## 検討した代替案
- **到着時刻で、追記のみ：** 古典的な定義ですが、このデータでは履歴に意味がありません。
- **未完了の注文 × 日ごとに1行：** 同じ答えのために数千万行になります。
- **毎回テーブル全体を上書き：** 単純ですが、修正が見えなくなります。
- **N 日を超えた注文を除外：** N は根拠のない数字になり、実際の問題が隠れます。

## 影響
- 毎回すべての履歴を再計算します（この規模では数秒）。新しい変更の影響を受けた日だけを作り直すことは、次の Change Data Feed のステップに含めます。
- テスト：`tests/test_backlog.py`（日の終わりのステータス、注文残から外れること、指標、止まった注文、購入前の変更、NULL にならないキー、削除を伴う修正）と、E2E のチェック2件（冪等な再実行、最終日がフルフィルメント・ファクトの未完了注文と一致すること）。
