# ADR-0004: 遅延データは販売日に計上する（許容は3日まで）

**ステータス:** 採用

## 背景
一部の注文明細は販売日の1〜2日後に届き、ごく一部は1週間遅れて届きます。レポートでは、売上は発生した日に計上されるべきです。一方で、過去の期間をいつまでも修正し続けると、既に報告した数値が安定しません。

## 決定
- すべての明細に `event_date`（購入日）と `arrival_lag_days`（バッチ日 − 購入日）を持たせ、Gold は `event_date` を基準にします。
- **3日以内**の遅延は受け入れます。Gold のファクトは粒度キーで MERGE するため、遅延明細は本来の日付に入り、影響を受けた日の数値が修正されます。
- **3日を超える**遅延は、ルール `too_late` として隔離し、`dq_metrics` に計上します。履歴が黙って変わるのではなく、人が意識的に判断できるようにするためです。
- 初回のバックフィルバッチは、履歴を運ぶことが目的なので対象外です。

## 検討した代替案
- **到着日で計上する:** 数値は安定しますが、日次売上が誤り、しかもその誤りに誰も気付きません。
- **どれだけ遅れても受け入れる:** 理論上は正確ですが、月末の数値が数週間後に変わり得ます。

## 影響
- 3日という許容値は業務上の判断であり、`Config.late_tolerance_days` で設定します。
- テスト: `test_each_bad_row_carries_every_rule_it_breaks`（3日と4日の境界）、`test_backfill_history_is_not_flagged_late`、`test_late_items_are_accepted_and_dated_by_the_sale`（E2E）。
