# ADR-0013: 2つの完全な実装を毎日突き合わせる

**日本語** | [English](../en/0013-two-implementations.md) | [中文](../zh/0013-two-implementations.md)

**ステータス:** 採用。ADR-0012 の判断（宣言型は参照用のみ）を置き換えます。

## 背景
ADR-0012 では、4つの仕組みと1つのファクトを Lakeflow Spark Declarative Pipelines で作り直し、本番の実装は命令型のみとしました。理由は3つの課題でした。業務ルール（セラーの最初のバージョンを 1900 年から有効にする）、Gold だけを止めるゲート、そしてローカルでテストできないことです。宣言型を書いてみると保守すべきものがずっと少ないことが分かったため、目標を変えました。仕様全体を宣言型でも、本番の実装として作ります。

## 決定
- **2つの実装はどちらも完全で、対等です。** `lakeflow/` は命令型が作るすべてのテーブルを作ります。Bronze、ルールのチェック、隔離、すべての Silver テーブル、メトリクス、ゲート、すべてのディメンション、3種類のファクト、マートです。書き込み先は `olist_sdp` です。
- **毎日並行して実行します。** `olist_daily` はバッチを配信し、命令型のタスクと宣言型のパイプラインを並行して実行したあと、`olist reconcile` で 16 テーブルを行単位で比較します（両方向の `EXCEPT ALL`）。差分が1行でもあればジョブを失敗させます。
- **命令型が「正解」です。** 宣言型のパイプラインはローカルで動かせませんが、命令型はローカルで単体テストと E2E テストを行っています。毎日の突き合わせが、宣言型のテストになります。
- **ダッシュボードは実装ごとに1つ**、同じスクリプトから生成します。

## 課題の解消
| 課題（ADR-0012） | 宣言型での解決 |
|---|---|
| ルールを二重に書く（エクスペクテーションと隔離） | 各 `checked_*` テーブルが、行が違反したルールを `_failed_rules` に列挙します（ルールは一度だけ書きます）。エクスペクテーションは名前で参照するだけ（アクションなし）なので、イベントログはルールごとに件数を記録します。隔離と Silver はその後で行を振り分けます。 |
| セラーの最初のバージョンが最初のスナップショットから始まる（ファクト行の97%にセラーがない） | `dim_seller` が `AUTO CDC FROM SNAPSHOT` の履歴を整形します。最も古いバージョンを 1900-01-01 から有効にし、`seller_sk = xxhash64(seller_id, valid_from)` で命令型と同じキーにします。 |
| ゲートが Gold だけでなく更新全体を止める | ジョブは `refresh_selection` でパイプラインを2回に分けて更新します。1回目は Bronze、Silver、隔離、メトリクス、`dq_gate`、2回目は Gold です。`dq_gate` は 5% を超えると自分の更新を失敗させるため、Gold の更新は始まりません。Free Edition で検証済みです。選択外のテーブルは `EXCLUDED` になり、失敗した更新で書かれた Silver は残り、次の更新で二重に書かれません。パイプラインは既定で失敗した更新を再試行しますが、データの問題では失敗が遅れるだけなので、`pipelines.numUpdateRetryAttempts` を 0 にしています。テストで閾値を 0.1% に下げると、ジョブは3分以内に失敗し、`sdp_gold` はスキップされました（`UPSTREAM_FAILED`）。 |
| ゲートが過去のすべてのバッチを毎回チェックする | `dq_gate` は最新のバッチだけを見ます。 |
| ローカルでテストできない | テスト済みの命令型との毎日の突き合わせで補います。 |
| 増分の Gold を手で書いている（ADR-0011） | Gold のテーブルはマテリアライズドビューです。どう更新するかはプラットフォームが選び、イベントログ（`olist_sdp.event_log` として公開）に記録します。フルリフレッシュでは再計算し、上流に新しいデータがない更新は `NO_OP` です。 |

## 突き合わせで見つかったこと
1. **再配信を取り込み時刻で順序付けていた。** 最初のフルリフレッシュでは、注文明細 10 行と、それから作るファクトが一致しませんでした。フルリフレッシュはすべての日を一度に取り込むため、全行の取り込み時刻が同じになり、「最初の配信を残す」がランダムな1件を選んでいました。翌日の再配信を残すと、到着の遅れが1日大きくなります。現在は両方の実装とも、ファイルパスにある配信日で順序付けています（`silver.py` の `first_delivery` / `latest_delivery`、宣言型のフローの `SEQUENCE BY`）。命令型の注文明細は偶然正しかっただけです。タイブレークに使うファイルパスが日付で始まっていたためです。顧客とレビューには日付による順序付けがまったくありませんでした。
2. この修正のあと、**16 のチェックがすべて一致**しました。Silver 6テーブル、ディメンション4つ、ファクト3つ、マート、隔離、ルールのメトリクスです。

## 残る違い（設計上のもの）
- **ゲートの意味。** 命令型のゲートは、その実行の入力を判定します。新しいデータがない実行は合格します。宣言型のゲートは最新のバッチを判定するため、不正なバッチがあると、データが修正されるまで Gold は止まったままです。どちらも Gold を守りますが、宣言型のほうが厳格です。
- **ゲートのログがない。** 宣言型のダッシュボードは、実行単位ではなく、メトリクスからバッチ単位でゲートを表示します。
- **隔離とメトリクスは集合として比較し**、重複排除の件数（info）は比較しません。命令型の運用テーブルは、バッチを再処理するともう一度追記するためです。
- **`refresh_selection` はジョブのパイプラインタスクのベータ機能です。**

## コード量
コメントと空行を除いて、宣言型は SQL と Python で約 550 行、命令型は同じ範囲（Bronze、品質、Silver、SCD2、ゲート、Gold、増分）の Python で約 1,070 行です。宣言型の SQL が ADR-0012 の 145 行より長いのは、仕様全体を持ち、命令型の Bronze と同じ JSON の解析も含むためです。

## 影響
- `olist_daily` にタスクが3つ増えました。`sdp_silver_and_gate`、`sdp_gold`、`reconcile` です。結果は `olist_ops.reconcile_log` に追記されます。
- `tests/test_pipeline_e2e.py` は、突き合わせる列がすべて命令型のテーブルに存在するかを確認します。列名を変えると、日次ジョブではなくローカルで失敗します。
- 解説ノートブック 10 は突き合わせを実行し、課題をどう解消したかを示します。
