# ADR-0009: 注文フルフィルメントの累積スナップショット・ファクト

**日本語** | [English](../en/0009-accumulating-snapshot-fulfillment.md) | [中文](../zh/0009-accumulating-snapshot-fulfillment.md)

**ステータス:** 採用

## 背景
`fact_order_item` はトランザクション・ファクト（注文明細ごとに1行）で、「何が売れたか」には答えられます。しかし「購入から配達までの時間がどこで掛かっているか」には答えられません。それは注文のライフサイクル全体（購入 → 承認 → 配送業者への引き渡し → 配達、またはキャンセル／在庫切れ）に関する性質だからです。

## 決定
- **`gold.fact_order_fulfillment`**：累積スナップショット。**1注文1行**で、マイルストーンが届くたびにその行を更新します（`order_id` で MERGE し、内容のハッシュが変わったときだけ書き直します）。
- **ソースは新設の `silver.order_changes`**：検証済みのステータス変更をすべて保存する追記専用のログで、キーは `(order_id, change_seq)`、更新は一切しません。`silver.orders` は現在の状態だけを持ち、ログはそこに至る経緯を持ちます。キャンセル・在庫切れの終了時刻はここから取得でき、監査証跡にもなります。**独自のチェックポイントを持つ別のストリーム**として動くため、既存の環境でも次回の実行で Bronze から全履歴を自動でバックフィルします。ルールは絞り込みのためだけに再評価し、隔離とメトリクスはこれまでどおり `orders` が1回だけ記録します。
- **マイルストーン**は注文の最新の変更から取得します（変更後イメージには、その時点までのすべてのタイムスタンプが入っています）。終了は最初の `canceled` / `unavailable` の変更で、理由は `end_reason` に入れます。
- **所要時間は時間単位**：`hours_to_approve`、`hours_to_ship`、`hours_in_transit`、`hours_total`、`hours_late`。`hours_late` は配達予定日の**終わり**から数えます。予定は日付なので、`is_on_time` と一貫させるためです。
- **ロールプレイング日付キー**：マイルストーンごとに1つ、すべて `dim_date` を指します。
- **セラーの列は持ちません。** 1つの注文に複数のセラーが含まれ得るため、セラー別の分析は `fact_order_item` で行います。注文レベルの指標は `item_count` と `order_value` です。

## タイムスタンプの不整合
段階の所要時間が負になった場合は NULL にし、注文に `has_inconsistent_milestones` を付けます。元のタイムスタンプは届いたまま保持します。警告レベルのメトリクス `inconsistent_milestones` を実行のたびに `ops.dq_metrics` に書き込みます（ゲートは無視します）。

実データでは 82,406 件中 628 件（0.76%）にフラグが付きます。

| 不整合の種類 | 注文数 |
|---|---:|
| 承認より前に配送業者へ引き渡し | 559 |
| 購入より前に配送業者へ引き渡し | 46 |
| 引き渡しより前に配達 | 23 |

ほとんどは数分の差で、システム間の時計のずれに見えます。数か月ずれているものはごく一部です。

**既知のギャップ：** Silver のルール `change_before_purchase` は、発火した変更そのものしか隔離しません。後続の変更は変更後イメージなので誤った引き渡し日時を持ち続け、`silver.orders` に入ります（46件）。この ADR では Silver の挙動は変えず、Gold のフラグで扱います。Silver で直すには個々のタイムスタンプを NULL にする必要があり、それは別の判断です。

## 検討した代替案
- **`silver.orders` だけからマイルストーンを取る：** 単純ですが、キャンセル注文の終了時刻も履歴もありません。
- **Bronze を直接読む：** 未検証のデータが Gold に入ります。
- **小さな負の差を時計のずれとみなす（N 時間以内なら 0 にする）：** N は根拠のない数字になります。業務側で許容範囲が決まったときの選択肢として残します。
- **フラグ付きの注文を除外する：** 0.76% の注文が黙って消えます。

## 影響
- 右側打ち切り（right-censoring）：直近の月は早く完了した注文しか段階が揃っていないため、平均が低めに出ます。ダッシュボードにその旨を記載しています。
- Change Data Feed による Gold の増分化は次のステップで、2つのファクトに同時に適用します。
- テスト：`tests/test_fulfillment.py`（マイルストーン、時間、日付キー、定時配達の境界、未完了の注文、終了理由、不整合なタイムスタンプ、その場での更新、追記専用ログ）と E2E のチェック2件。
