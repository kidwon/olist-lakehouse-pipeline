# ADR-0012: 同じ仕様を Lakeflow Declarative Pipelines で実装して並べて比較する

**日本語** | [English](../en/0012-lakeflow-comparison.md) | [中文](../zh/0012-lakeflow-comparison.md)

**ステータス:** 採用

## 背景
ADR-0008 では、仕組みそのものを示すために命令型（Structured Streaming + MERGE）を選び、Lakeflow ならそれぞれ「キーワード1つ」で書けると述べました。この ADR では、その主張を検証します。4つの仕組み（取り込み、前進のみの CDC、スナップショットからのセラー SCD2、隔離を伴う注文明細の品質チェック）と Gold のトランザクション・ファクトを、`lakeflow/` に宣言型で作り直しました（SQL で書けない部分は Python）。パイプラインは**同じランディングファイル**を読み、独自のスキーマ `olist_sdp` に書き込むため、両者を突き合わせられます。Free Edition では種類ごとに同時に動かせるパイプラインが1つだけなので、常時稼働ではなくトリガー実行にしています。

## 実データでの突き合わせ
| チェック | 命令型 | Lakeflow | 結果 |
|---|---:|---:|---|
| Silver の注文（行数、ID + ステータス + change_seq） | 82,406 | 82,406 | 一致 |
| Silver の注文明細（行数、キー） | 93,465 | 93,465 | 一致 |
| ルール別の隔離件数（欠落 / 価格 / 遅延 / 不明） | 9 / 11 / 5 / 3 | 9 / 11 / 5 / 3 | 一致 |
| Gold ファクトの行（キー項目） | 93,465 | 93,465 | 一致 |
| ゲート：最大の不正率 | 2.11% | 2.11% | 一致 |
| セラー履歴（行数、クローズ済みバージョン） | 3,173、78 | 3,173、78 | 一致（下記の修正後） |
| セラーのバージョンがないファクト行 | 0 | 91,085（97%） | **設計上の違い** |

## Lakeflow のほうが簡潔な点
- **コード量：** 同じ仕組みが、命令型の約450行に対して約145行（SQL + Python）です。厳密な1対1の比較ではありませんが、差は確かです。
- **前進のみの CDC** は `AUTO CDC ... SEQUENCE BY change_seq` のフロー1つで済み、チェックポイントや MERGE の条件は不要になります。
- **重複排除**は、業務キーをキーにした `AUTO CDC` で済みます。
- **品質メトリクスが自動で得られます：** イベントログにエクスペクテーションごとの合格・不合格の行数が記録され、件数は `ops.dq_metrics` とちょうど一致します。
- **スナップショットにバージョンがあります：** `AUTO CDC FROM SNAPSHOT` は、前回より新しいスナップショットだけを適用します。突き合わせの結果、これが命令型の見落としを防ぐことが分かりました（次の節）。

## 比較で見つかった命令型の問題
セットアップのジョブが手動で再実行され、リプレイがリセットされて、2018-05-31 のバックフィルのファイルが再配信されました。命令型の SCD2 は古いスナップショットを変更とみなし、移転した78件のセラーを元の都市に戻してしまい、開始より前に終わるバージョンができました。Lakeflow は再配信されたスナップショットを無視しました。命令型での修正は次のとおりです。
- `scd2.apply_snapshot` は、最後に適用したもの（テーブルプロパティに保存）より新しくないスナップショットをスキップします。修正がないと失敗する回帰テストも追加しました。
- `replay.prepare` は、既にバッチを配信したリプレイを、`--force` を指定しない限りリセットしません。
- Databricks 上では `RESTORE TABLE ... TO VERSION AS OF 12`（Delta のタイムトラベル）でテーブルを戻し、`full_refresh=true` で Gold を作り直しました。

## Lakeflow で回避策が必要な点、仕様どおりにできない点
- **SCD2 の最初のバージョン：** 仕様（ADR-0003）では、セラーの最初のバージョンは 1900-01-01 から有効です。Lakeflow では最初のスナップショットの日から始まるため、**ファクト行の97%（2018-05-31 より前の注文）が、どのセラーのバージョンにも結び付きません。** このような業務ルールには上に一層追加する必要があり、簡潔さの多くが失われます。
- **過去のスナップショットには Python が必要：** SQL の形式は、テーブルを現在の状態でスナップショットします。1日1つのスナップショットを順に再生するには、バージョン関数を使う `create_auto_cdc_from_snapshot_flow` が必要です。
- **隔離には2つ目のテーブルが必要：** エクスペクテーションは行を捨てて数えるだけで、保存はしません。同じルールを反転させて隔離テーブルに書き込むため、各ルールを2回書くことになります。
- **ゲートは模倣：** 集計に対する `EXPECT ... ON VIOLATION FAIL UPDATE` は、Gold だけでなく更新全体を止めます。また、更新のたびにこれまで受け取ったすべてのバッチを評価し直すため、過去に1つ不正なバッチがあると、それに対処するまで以後のすべての更新が失敗します。
- **ローカルでテストできない：** パイプラインは Databricks 上でしか動きません。命令型のコードは、ノート PC と CI 上の pytest で動きます（テスト64件とノートブック）。こちらの正しさは突き合わせに頼っています。

## 決定
このリポジトリでは、命令型のパイプラインを主な実装として維持します。エンドツーエンドでテストでき、業務ルール（1900 年からの開始、Gold だけを止める比率ゲート）を正確に表現できるからです。Lakeflow 版は、参照実装および突き合わせのチェックとして残します。こうした業務ルールのない新しいチームのパイプラインであれば、Lakeflow を標準にするのが妥当です。コードがはるかに少なく、メトリクスとスナップショットのバージョン管理も最初から備わっています。

## 影響
- `resources/olist_sdp.yml` がバンドルでパイプラインをデプロイします。解説ノートブック [`10_lakeflow_comparison`](../../../notebooks/walkthrough/10_lakeflow_comparison.py) が Databricks 上で突き合わせを実行します。
- ADR-0003 を補足します。スナップショットは時間とともに前に進まなければならず、今はコードでそれを強制しています。
